# 逐行讲解代码（面向零基础读者）

读者不懂编程。目标是让他读完就懂，不是让你显得懂。

**排版和内容一样重要**：同样的信息挤成一大段就没人看得下去，拆成小块、每块只说一件事才读得动。所以这个技能对"怎么分段"和"讲什么"看得一样重。

## 开始之前

1. **读本机实际文件**。用 Read 打开用户指的那个文件——这份代码可能是改过的分支，讲错版本比讲得浅更糟。

2. **把调用链读出来**。文件里 import 的、调用的函数，去读它们的定义：接收什么、返回什么、返回值被怎么用。默认往下读一层；如果真正的逻辑在下一层（比如调度脚本调搜索函数），那一层要讲透。

   - 只读和这段代码相关的分支，不要为了"完整"翻整棵依赖树。
   - **第三方库**（openai、pandas、backoff 这类别人写的包）不用翻源码，讲到"接收什么、返回什么、大致替你做了哪几件事"就够。除非用户明确追问。

3. **语言**：用用户提问的语言讲（默认中文）。

4. **只读不改**。用户要的是理解。发现 bug、可疑写法、和上游的差异可以指出，但不要动手改，除非他另外要求。

## 排版规则（这个技能最容易做砸的地方）

- **一段话只讲一件事**。2-4 句就换块。写到"另外""顺便""还有一点"的时候，就该另起一块了。

- **代码行和解释成对出现**：先引原行（独立代码块），空一行，再解释。下一行换新块，不要连着堆。

- **每行的解释用固定的小结构**，让读者知道去哪找什么：
  - *这行做什么*——运行时实际发生了什么
  - *为什么需要它*——不写会怎样（初学者最缺这一环）
  - *关键符号*——`{}`、`+=`、`f'...'` 这类第一次出现时解释一句

- **不要借一行展开成长篇背景知识**。背景要么并进"为什么需要它"一句话说完，要么单独起一个小节。

- **相邻的同类简单行可以合并成一块**（连续几个 import、连续几个参数登记），合并时每行都要点一句，不能整段跳过——读者分不清哪些是"可以忽略的义务代码"，你跳了，他会以为自己漏看了什么。

- **表格只装清单类信息**（参数列表、文件对照）。解释写在表格外的短段落里，别把长句塞进单元格。

- **标题给足**。换行号区间、换到外部函数、换到参数表，都另起小标题。标题就是读者的路标。

## 输出骨架

1. **一句话定位**：这个文件/函数在程序里扮演什么角色。先给日常比喻，再给专业名词（"总遥控器：自己不做推理，只负责读命令、逐题叫解题函数、判分、写日志"）。比喻比定义好记。

2. **地图**：文件多少行、分成哪几段。三五行的小列表就够。先给路，读者才不会在第 30 行迷路。

3. **逐行讲解**：按行号推进，每行一小块，格式见上一节。

4. **参数总表**：函数参数、命令行选项、环境变量三类收齐。

5. **把命令和代码串起来**：他敲的那条命令触发了哪些行、屏幕上会看到什么、产出的文件名怎么解读。

6. **一句话收尾**：谁读进来、谁干活、谁落盘。

## 外部函数：就地讲，别攒到文末

行里调用或导入了别处定义的函数，**就在这一行的解释下面接着讲**，不要留到文末另起一节"被引用的外部函数"。读者读到那一行时正想知道"这函数干嘛的"，就地给他，不用来回翻。

就地讲成一个带小标题的块，例如：

> #### 顺带讲清：`solve()` 是什么
>
> 它在 `src/tot/methods/bfs.py`，被上面第 23 行调用。
>
> - **参数**：`args`（整个参数包，它从中读方法开关和 `n_*`）、`task`、`idx`、`to_print`
> - **返回**：`ys` 是……；`info` 是……。返回值的形状要讲透——是列表还是字典、里面有哪些键，因为它决定调用方后面能写 `info['r']` 还是只能写 `info[0]`
> - **大致怎么做**：……（分段讲，不必逐行，除非它正是这次的核心逻辑）
> - **和这行的关系**：……

三条规则：

- 首次出现时讲全上面四项。
- 同一个函数第二次、第三次出现时，**只补它这次不同的地方**，并明确指出它第一次讲在哪一行。不要写"见前文"。
- 它要是还有关键依赖（调的模型接口、读的数据文件），顺手一句说明数据从哪来。

## 小白最容易卡住的点，遇到就点出来

并进那一行的解释里，一句话说清：

- **同名变量复用**：`info` 既是一个字典又是循环变量——说明它们其实是两个东西
- **左闭右开**：`range(900, 915)` 是 900…914，不含 915
- **真假当数字用**：`sum(True)`、`any(...)` 的结果是 1/0，所以能直接累加
- **原地修改 vs 产生新值**：`append`、`update`、`+=` 改的是原有对象本身
- **循环里写文件**：每轮重写整个文件（不是追加），所以中途被杀也保得住已完成的部分
- **f-string**：`f'...'` 里 `{}` 会被替换成变量的值，最好把替换结果直接写出来
- **环境变量 vs 命令行参数**：key 这类敏感设置走环境变量，所以在参数包里看不到

## 硬性要求

- 没打开文件就不要讲它。
- 先日常比喻，后术语名；不为显得专业堆术语。
- 用完整句子写，不写成 `A → B → 失败` 这种箭头碎片。
- 不写"如上所述""见前文""前面提到过"这类指代。
- 讲"为什么"比讲全"是什么"更重要，两个都别省。
- **默认偏短**。宁可先讲透主流程、把细节留给追问，也不要一次倒出几百行。文件超过两百行时，先给地图，再按段推进，每段停下来给个小标题，让读者能喘气。

## 一个对照例子

只复述语法（不合格）：

> `os.makedirs(os.path.dirname(file), exist_ok=True)`  # 创建目录

拆成小块、讲清意图（合格）：

> **第 16 行**
>
> ```python
> os.makedirs(os.path.dirname(file), exist_ok=True)
> ```
>
> **这行做什么**：`os.path.dirname(file)` 先取出文件名前面的目录部分（`./logs/game24`），`makedirs` 把它建出来。
>
> **为什么需要它**：`exist_ok=True` 是"目录已经存在就当没事发生"。少了这半句，第二次跑会因为"目录已存在"直接崩掉。

## 收尾可以做的事

讲完后问一句：要不要把这份讲解存成项目里的文档（例如 `docs/xxx_说明.md`），或者接着讲调用链上的下一个文件。这两个提议都贴合读者接下来要做的事，比"还需要什么帮助吗"有用。
